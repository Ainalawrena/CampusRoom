Phase 1 — Prototype HTML/CSS (terminée)

Un prototype statique fidèle à un PDF de wireframes + une palette imposée (Ash Grey 
#CAD2C5, Muted Teal 
#84A98C, Deep Teal 
#52796F, Dark Slate 
#354F52, Charcoal Blue 
#2F3E46). Pas de framework CSS, JS minimal. Un fichier HTML + un CSS par écran, tous reliés entre eux. Écrans couverts : connexion/inscription, puis les 4 parcours par rôle (Étudiant, Enseignant, Logistique, Administrateur) avec leurs listes, détails, tableaux de bord et formulaires respectifs. Ce prototype sert maintenant de référence visuelle et fonctionnelle pour la vraie application.

Phase 2 — Vraie stack : React + Laravel (en cours)

Organisation : un seul repo Git (monorepo) — https://github.com/Ainalawrena/CampusRoom — avec deux dossiers indépendants backend/ (Laravel) et frontend/ (React), chacun avec ses propres dépendances (composer.json / package.json).

Choix techniques (pris pour aller vite, contrainte de 2 jours) :

Auth : Laravel Sanctum (auth SPA standard, tokens, pas d'OAuth lourd)
État côté React : Context API + hooks natifs (pas de Redux/Zustand)
Style : les mêmes fichiers CSS/tokens que le prototype, pas de passage à Tailwind

└── composer.json, .env.example, artisan, bootstrap/app.php

Logique métier clé : dans routes/api.php, les routes sont groupées par niveau d'accès — public (login/register), authentifié (salles en lecture, réservations), puis role:logistique,administrateur (valider/refuser une réservation), puis role:administrateur (CRUD salles, gestion utilisateurs). Dans ReservationController::store, une réservation faite par un enseignant est directement confirmee, alors qu'un étudiant passe par en_attente — ça reproduit la différence "Validation requise" vue dans le wireframe.

Différence importante avec le prototype : dans le HTML statique, chaque rôle avait ses propres fichiers dupliqués (salle-reservation-etudiant.html vs -enseignant.html, etc.). En React, une seule RoomListPage.jsx sert aux deux rôles — la sidebar et les droits changent dynamiquement selon user.role, pas de duplication de code. Autre différence : la page de connexion n'a plus de sélecteur de rôle factice — le rôle vient du compte utilisateur renvoyé par l'API après login, ce qui est plus correct.

Fonctionnement d'ensemble
React (port 5173 par défaut) appelle l'API Laravel (port 8000) via Axios, avec un token Sanctum stocké en localStorage et injecté automatiquement sur chaque requête
AuthContext garde l'utilisateur connecté en mémoire, ProtectedRoute bloque l'accès aux pages selon le rôle
Laravel expose tout sous /api/*, avec CORS configuré pour n'accepter que l'origine du front (FRONTEND_URL dans .env)
Le DatabaseSeeder permet de retrouver immédiatement les mêmes comptes/données que dans le wireframe pour tester chaque rôle
